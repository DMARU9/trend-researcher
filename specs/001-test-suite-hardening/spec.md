# Feature Specification: テスト拡充によるパイプライン信頼性の向上

**Feature Branch**: `001-test-suite-hardening`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "現状のプロジェクトはテストが足りていないです。テストを作成して、もっと信頼性を上げるようにしてください。そのための仕様書を作成してください。"

## 背景と現状の実測

仕様の前提となる事実（2026-09-12 実測）。ここに挙げた数値は「改善前の基準値」であり、要件ではない。

| 観測項目 | 実測値 |
|----------|--------|
| テスト件数 / 実行時間 | 61 件 / 1.5 秒（全件 green） |
| 全体の行カバレッジ | 82%（1206 文中 214 文が未実行） |
| CLI エントリ（`__main__.py`） | 0%（79 文が未検証） |
| X 検索ツール（`tools/x_search.py`） | 45%（リトライ・例外・0 件経路が未検証） |
| 中間成果物の読み戻し（`cache.py`） | 38% |
| 字幕パーサ（`tools/transcript.py`） | 79% |
| 共通ネタ抽出（`nodes/extract_common.py`） | 79% |
| 指示解釈（`nodes/parse_instruction.py`） | 85% |

未検証が集中しているのは次の 3 領域である。

1. **CLI の外部契約**（終了コード 0/1/2、stdout はレポートのみ・stderr は進捗とエラー）— テストが 1 件もない。
2. **外部サービス境界の失敗経路**（X のレート制限・スレッド取得失敗、字幕なし、キャッシュ書き込み失敗）— 成功経路のみが検証されている。
3. **LLM 自由文の解釈の分岐**（件数・投稿日下限・出力形式の優先順位、崩れた Markdown/JSON の扱い）。

あわせて、件数だけでは見えない懸念がある。既存 61 件には、対象の振る舞いを削っても緑のままになり得るテストが含まれる（例: グラフ構築テストが「None でない」ことだけを確認している、実行時設定の検証が 3 つのファイルに重複している）。信頼性は件数やカバレッジ率ではなく「落ちるべきときに落ちるか」で決まる。

## Clarifications

### Session 2026-09-12

- Q: FR-019 / SC-002 の「カバレッジ 90% 以上」はどの単位で判定するか → A: 対象範囲の合計で 90%（個別モジュールごとの下限は要求しない）
- Q: FR-023 の「検出された実装不具合」をどう扱うか → A: 本機能の範囲で最小修正する（独立した修正タスクへの切り出しで代替しない）
- Q: SC-005 の「テスト件数の増加」をどう判定するか → A: 純増（追加数 − 削除数）が正であること。かつ追加分を CLI 契約・失敗経路・LLM 解釈分岐の領域別に説明できること
- Q: Edge Case「同一の識別子を持つ候補が重複して返る」をどう固定するか → A: 既存の契約（重複は除去し取得順を維持）を要件化して固定する（付随する挙動として Edge Cases から削除しない）
- Q: 重複除去が X にのみ実装され YouTube に無い非対称をどう扱うか → A: 非対称を仕様として明示する（YouTube は単一クエリのみのため重複除去を要求しない。当該要件は X に限定する）
- Q: Edge Case「指示文が空文字である」の期待は何か → A: 引数エラー（終了コード 2）として固定する。実測では `""` と `"   "` はいずれも argparse を通過して受理され、そのまま `parse_instruction` が空の指示で LLM を呼ぶ。これは引数検証の欠落であり、要件として固定する（**FR-025**）
- Q: Edge Case「プラットフォーム名の大文字小文字の揺れ」の期待は何か → A: 正規化しない。`--platform X` は未知の値として引数エラー（終了コード 2）とする（実測: `argparse(choices=...)` がその挙動を示す。**CLI-001-10**）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - CLI の外部契約を回帰から守る (Priority: P1)

開発者として、CLI にどの入力を与えると何が stdout に出て、何が stderr に出て、終了コードが何になるかを自動テストで固定したい。パイプラインを外部から検証できる唯一の入口が CLI であり、そこだけテストが 1 件もない状態では、契約の破壊に気づけないためである。

**Why this priority**: CLI は利用者が唯一直接触れるインターフェースであり、終了コードと出力チャネルは利用者のスクリプトや自動化が依存する契約である。ここが壊れると利用者側で静かに誤動作する。さらに現状のカバレッジは 0% で、最も検証が薄い領域である。

**Independent Test**: CLI を実行プロセスとして起動し（外部 I/O は模擬）、観測された stdout・stderr・終了コードのみを検証すれば完結する。他のストーリーに依存しない。

**Acceptance Scenarios**:

1. **Given** 正常にレポートが得られる指示, **When** CLI を実行する, **Then** stdout にはレポートのみが出力され、進捗は stderr に出て、終了コードは 0 である
2. **Given** レポートの出力先が指定されている, **When** CLI を実行する, **Then** レポートはファイルに書かれ、stdout にレポートは出力されず、完了メッセージが stderr に出て、終了コードは 0 である
3. **Given** 出力形式に JSON が指定されている, **When** CLI を実行する, **Then** stdout は解析可能な JSON のみで構成される
4. **Given** 投稿日の下限に不正な形式の値が指定されている, **When** CLI を実行する, **Then** stderr にエラーが出て終了コードは 2 である
5. **Given** 必須のオプションが欠落している、または未知のプラットフォーム名が指定されている, **When** CLI を実行する, **Then** 終了コードは 2 である
6. **Given** 実行中に想定外の失敗が起きる, **When** CLI を実行する, **Then** stderr にエラーが出て終了コードは 1 である
7. **Given** 検索結果が 0 件である, **When** CLI を実行する, **Then** 後続の解析を行わず、理由が stderr に出て、終了コードは 0 である
8. **Given** 要求件数より実際に取得できた件数が少ない, **When** CLI を実行する, **Then** 不足の情報が stderr に出て、終了コードは 0 である
9. **Given** 実行が時間上限に達する, **When** CLI を実行する, **Then** 警告が stderr に出て終了コードは 1 である

---

### User Story 2 - 外部サービスの失敗経路でも壊れないことを保証する (Priority: P2)

開発者として、X の検索・スレッド取得、YouTube の字幕取得、中間成果物の書き込みといった外部依存が失敗したときに、パイプラインが落ちずに縮退して動作し、その理由が利用者に伝わることをテストで固定したい。外部依存は「普段は成功する」ため、失敗時の分岐が最も検証されないまま残るからである。

**Why this priority**: 外部依存の失敗は本番で必ず起きる（レート制限、クッキー失効、字幕なし）。現状は成功経路だけが検証されており、縮退処理を誤って削っても気づけない。加えて現状 45% / 79% と検証が薄い。

**Independent Test**: 各境界の処理を、外部サービスの模擬（例外・空応答・部分応答）で呼び出し、戻り値と利用者への通知のみを検証すれば完結する。

**Acceptance Scenarios**:

1. **Given** X の検索が規定回数リトライしても失敗する, **When** 検索を実行する, **Then** 失敗が呼び出し元に伝播し、利用者に理由が示される
2. **Given** X のスレッド取得が失敗する, **When** 付加情報の取得を実行する, **Then** 本文のみで解析が続行され、失敗の理由がレポートの備考に残る
3. **Given** YouTube の字幕が取得できない, **When** 付加情報の取得を実行する, **Then** 「字幕取得不可」の理由が備考に残り、メタデータのみで解析が続行される
4. **Given** 検索結果が 0 件である, **When** 検索処理を実行する, **Then** 後続の取得・解析をスキップしてレポート生成へ進む
5. **Given** 中間成果物の出力先に書き込めない, **When** レポートを生成する, **Then** 処理は成功し、書き込み失敗の理由が進捗に現れる
6. **Given** 中間成果物が存在しない, **When** 読み戻しを実行する, **Then** 例外ではなく「なし」を返す
7. **Given** 字幕が JSON3 形式または VTT 形式で与えられる, **When** 字幕を解析する, **Then** タイムスタンプとインラインタグを除いた本文が得られる
8. **Given** 外部サービスの応答に投稿日が欠落している、または不正な形式である, **When** 候補へ変換する, **Then** 投稿日は未設定として扱われ、処理は続行する

---

### User Story 3 - LLM の自由文出力に対する決定的な解釈を固定する (Priority: P3)

開発者として、外部 LLM が返す揺れのある自由文から、件数・投稿日下限・出力形式・検索クエリ・共通テーマをどう解釈するかを、分岐ごとにテストで固定したい。LLM の出力形式は崩れることが前提であり、本番の正しさはフォールバックの設計で決まるからである。

**Why this priority**: 形式が崩れたときの解釈は利用者の意図（件数・期間・出力形式）の取り違えに直結する。現状は正常系が中心で、崩れた入力の扱いが部分的にしか検証されていない。

**Independent Test**: 解釈処理に固定の入力（指示文・LLM 応答の模擬）を与え、解釈結果のみを検証すれば完結する。

**Acceptance Scenarios**:

1. **Given** 指示本文に件数と期間（例:「5件」「半年以内」）が含まれ、他に指定がない, **When** 指示を解釈する, **Then** 件数と投稿日下限が本文の指定どおりに解決される
2. **Given** コマンドラインまたは実行時設定で件数・出力形式が指定され、指示本文に別の指定がある, **When** 指示を解釈する, **Then** 明示的な指定が優先される（優先順位: 明示指定 > 本文の自然言語 > LLM の解釈）
3. **Given** 指示本文に明示的な日付（例:「2025-01-01 以降」）が含まれる, **When** 指示を解釈する, **Then** 投稿日下限がその日付として解決される
4. **Given** 日付として解釈できない文字列が与えられる, **When** 指示を解釈する, **Then** 投稿日下限は未設定となり、例外にはならない
5. **Given** LLM が構造化されたブロックを返さない, **When** 指示を解釈する, **Then** 指示本文全体がトピックとして扱われ、既定値で処理が続行される
6. **Given** LLM の共通ネタ出力が見出しと本文のみで構成される, **When** 共通ネタを解析する, **Then** テーマ名と説明が抽出され、解析対象の全コンテンツが該当として紐づく
7. **Given** LLM の共通ネタ出力が空である, **When** 共通ネタを解析する, **Then** テーマ一覧は空になり、レポートには「特筆すべき共通点なし」が出力される
8. **Given** 活用アイデアの表が崩れている（列不足・見出しのみ・区切り行のみ）, **When** 解析する, **Then** 該当行は破棄され、例外にはならない
9. **Given** LLM が検索クエリに年号や期間表現を混入させる, **When** 検索クエリを生成する, **Then** 年号・期間表現が除去され、空になった行は捨てられる

---

### User Story 4 - 既存テストが「落ちるべきときに落ちる」ことを保証する (Priority: P4)

開発者として、既存テストが対象の振る舞いを実際に検証しているか（恒真アサートや実装の写しになっていないか）を点検し、無効なテストを強化または統合したい。件数とカバレッジだけを増やしても、無効なテストが残っていれば信頼性は上がらないからである。

**Why this priority**: プロジェクト憲法は「対象の挙動を削っても緑のままのテストは無効」と定めている。現状の 61 件にはその疑いがあるテストが含まれ、テストの存在そのものが保証になっていない。ただし新規追加（P1〜P3）より優先度は低い。

**Independent Test**: テスト対象の振る舞いを一時的に変異させ、対応するテストが失敗することを確認する（変異は必ず元に戻す）。この手順だけで完結する。

**Acceptance Scenarios**:

1. **Given** 既存テストの一覧, **When** 各テストについて「対象の振る舞いを壊したら失敗するか」を確認する, **Then** 失敗しないテストは強化または削除され、その判断が記録される
2. **Given** グラフの配線（ノード順・検索 0 件時の分岐）, **When** 配線を変更する, **Then** 対応するテストが失敗する
3. **Given** 進捗表示の総数とパイプラインのノード数, **When** 両者の整合を壊す, **Then** 対応するテストが失敗する
4. **Given** 同一の振る舞いを複数ファイルで検証しているテスト, **When** 監査する, **Then** それらは 1 箇所へ統合される

---

### Edge Cases

- 検索結果が 0 件 / 1 件 / 要求件数より少ない（境界）
- 同一の識別子を持つ候補が複数のクエリの結果として重複して返る（X。YouTube は単一クエリのため対象外）
- 投稿日が欠落・不正形式・未来日付である
- 字幕テキストが空文字または空白のみである
- LLM が表の列を欠いた Markdown、または JSON ブロックを含まない応答を返す
- レポートの出力先が書き込み不可である
- 指示文が空文字である
- stdout がリダイレクトされた非対話環境で、進捗とレポートが混ざらない
- プラットフォーム名の大文字小文字の揺れ、および未知の値
- 実行時間の上限に到達する

## Requirements *(mandatory)*

### Functional Requirements

以下は本機能の成果物である「テストスイート」が満たすべき要件である。

- **FR-001**: テストスイートは、ネットワーク接続と実認証情報（API キー、クッキー、アカウント DB）なしで全件完走 MUST。実サービスへの通信を要求するテストを含めてはならない
- **FR-002**: CLI の終了コードと出力チャネルの分離は、実行プロセスの観測結果として検証 MUST（関数の戻り値のみで代替しない）
- **FR-003**: CLI の成功経路について、stdout がレポートのみ・stderr が進捗とログ・終了コード 0 であることを固定 MUST
- **FR-004**: 引数の検証エラー（必須オプションの欠落、未知のプラットフォーム値、不正な日付形式）が終了コード 2 で終わることを固定 MUST
- **FR-005**: 実行時の失敗（想定外の例外、時間上限到達）が終了コード 1 で終わり、理由が stderr に出力されることを固定 MUST
- **FR-006**: レポート出力先が指定された場合、ファイルへ書き出され stdout にレポートが出ないことを固定 MUST。書き込みに失敗した場合（親ディレクトリが存在しない・書き込み不可・ディレクトリを指定した）は終了コード 1 で終わり、理由が `[エラー]` 形式で stderr に出力され、生のスタックトレースを出さないことを固定 MUST
- **FR-007**: 検索結果が 0 件のとき、後続の取得・解析をスキップして正常終了し、理由が stderr とレポートの備考に残ることを固定 MUST
- **FR-008**: 要求件数より取得件数が少ないとき、その不足が利用者に通知され、処理は正常終了することを固定 MUST
- **FR-009**: 外部サービスの例外・空応答・部分応答に対し、パイプラインが縮退して継続し、理由が備考に残ることを固定 MUST
- **FR-010**: リトライを伴う外部呼び出しは、待機時間を実時間で消費せずに検証できる MUST
- **FR-011**: LLM 自由文からの指示解釈について、件数・投稿日下限・出力形式・トピックの優先順位を分岐ごとに固定 MUST
- **FR-012**: LLM 自由文の解析（構造化ブロック・見出し・表・リスト）は、正常系と崩れた入力の両方で固定 MUST
- **FR-013**: 字幕解析は、複数の字幕形式と、タイムスタンプ・インラインタグの除去を固定 MUST
- **FR-014**: 中間成果物の書き込みと読み戻しの契約（配置・文字コード・存在しない場合の戻り値）を固定 MUST
- **FR-015**: パイプラインのノード数・進捗の総数・グラフの配線（ノード順、0 件時の分岐）の整合を固定 MUST
- **FR-016**: 無効なテスト（対象の振る舞いを削っても緑のままのテスト、実装の写し、恒真アサート、実行されない補助テスト）を検出した場合、強化または削除 MUST
- **FR-017**: 同一の振る舞いを複数箇所で検証している重複テストは、1 箇所へ統合 MUST
- **FR-018**: カバレッジを単一のコマンドで計測でき、未実行行を特定できる MUST。計測は開発時のみの依存で実現し、プロダクション依存を増やしてはならない
- **FR-019**: 対象範囲は `src/trend_researcher/` 配下の全モジュールとし、その行カバレッジは `--cov=trend_researcher` の**合計行**で 90% 以上 MUST。判定は合計値で行い、個別モジュールごとの下限は要求しない（現状: 合計 82% / CLI 0% / X 検索ツール 45%）。除外設定は行わない（宣言のみのモジュールを除外しても合計は 0.2 ポイントしか変わらないため。`contracts/coverage-policy.md` COV-002）。ただし、CLI の外部契約（FR-002〜FR-008）と外部サービスの失敗経路（FR-009）の検証は、合計値とは独立に要求する
- **FR-020**: テストスイート全体の実行時間は 60 秒以内 MUST
- **FR-021**: 非決定性（現在時刻・乱数・並列順序・待機）はテスト側で固定 MUST。テスト結果が実行環境や実行順序に依存してはならない
- **FR-022**: 既存テストは、無効と判定されたものを除き green を維持 MUST。テストを通すために期待値を実装の挙動へ書き換えてはならない
- **FR-023**: テスト追加の過程で検出された実装側の不具合（ドキュメントと実装の不一致を含む）は、**本機能の範囲で修正** MUST。独立した修正タスクへの切り出しで代替してはならない（MUST NOT）。修正の際は、修正を元に戻すと対応するテストが失敗することを確認 MUST。黙示的にテスト側の期待値を実装に合わせてはならない（MUST NOT）。既検出の不具合（レポート出力先への書き込み失敗時に生のスタックトレースが stderr に出る）はこの条項の対象である
- **FR-024**: 同一の識別子を持つ候補が複数の検索クエリの結果として重複して返る場合、X の検索は重複を除去し、取得順（関連度順）を維持 MUST。除去後の件数が要求件数を超える場合のみ要求件数まで截断 MUST。重複の除去は取得順の先勝ちとし、同一識別子の候補を統合（本文・反応数のマージ）してはならない（MUST NOT）。YouTube は単一クエリのみを検索するため重複が発生する経路がなく、この要件の対象外とする

- **FR-025**: 指示が空文字または空白のみの場合、CLI は外部接続より前に引数エラーとして検出し、終了コード 2 と `[エラー] 指示を指定してください。` を stderr に出力することを固定 MUST。空白のみの指示を有効な指示として受理してはならない（MUST NOT）

### Key Entities *(include if feature involves data)*

- **テストスイート**: 単体テスト（決定的な変換・解析・モデル・設定）と統合テスト（パイプライン全経路・CLI 経路）の 2 層。配置は既存の構成に従う
- **検証対象の境界**: CLI エントリ、パイプラインのノード群、外部サービス境界（X の検索とスレッド、YouTube の検索と字幕）、プラットフォーム抽象、中間成果物の永続化
- **模擬外部依存**: LLM、X、YouTube、ファイルシステム、現在時刻、待機
- **観測点**: 終了コード、stdout、stderr、生成物（レポート文字列、中間成果物）
- **カバレッジ計測結果**: 現在値（全体 82%）と目標値（90%）、および未実行行の一覧
- **無効テスト判定の記録**: 強化・削除・統合したテストとその判断理由

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ネットワークと実認証情報を一切使わずに、テストスイートが全件 green で完走し、実行時間が 60 秒以内である（現状 1.5 秒・61 件）
- **SC-002**: 対象範囲（`src/trend_researcher/` 配下の全モジュール）の行カバレッジが `--cov=trend_researcher` の**合計行**で 90% 以上である。個別モジュールごとの下限は判定に含めない（現状: 合計 82% / CLI 0% / X 検索ツール 45%）。合計値の達成のみを理由に、CLI 契約（SC-003）や失敗経路（SC-004）の検証を省略することは認めない
- **SC-003**: CLI の終了コード 3 種（0 / 1 / 2）と stdout・stderr の分離がテストで固定されており、いずれか 1 つの契約を変更すると対応するテストが失敗する
- **SC-004**: 主要な失敗経路（外部サービスの例外、字幕なし、検索 0 件、書き込み失敗、LLM 出力の崩れ、時間上限到達）のそれぞれに対応するテストが存在し、該当する縮退処理を取り除くとテストが失敗する
- **SC-005**: テスト件数の**純増**（追加数 − 削除数）が正であり、追加分が CLI 契約・失敗経路・LLM 解釈分岐のどの領域に対応するかを説明できる（基準値: 変更前 61 件。統合・削除の対象はルート直下の 19 件）
- **SC-006**: 無効と判定して強化・削除・統合した既存テストを一覧でき、件数の増加だけで信頼性が上がったと主張していない

## Assumptions

- テストの配置は既存構成とプロジェクト憲法に従う（決定的な変換・解析の単体は単体テスト層、パイプライン全経路と CLI 経路は統合テスト層）
- 外部依存の模擬は既存踏襲の手法（標準のモック機構で境界を差し替える）を用い、新しいモック基盤は導入しない
- CLI の契約検証は実行プロセスの起動によって行う。その分の実行時間増は 60 秒以内に収める
- カバレッジ計測は開発時のみの依存として追加してよい。プロダクション依存と実行時依存は増やさない
- カバレッジ目標 90% の対象範囲は CLI・ノード・外部境界ツール・provider とする。宣言のみのモジュール（パッケージ初期化、プロンプト定数）は母数から除外して評価する
- 中間成果物は「書き込み専用」の設計（読み戻し経路は未実装）であるため、読み戻し関数の検証は契約（存在しない場合は「なし」を返す）の固定に留める
- 実 API を使う手動スモーク（README 記載の確認手順）は本スコープ外であり、自動テストの合否条件に含めない
- 検出された実装側の不具合は、**本機能の範囲で修正する**（独立した修正タスクへの切り出しで代替しない。FR-023）
- 実行環境は Python 3.11 以上と `uv` が利用可能であることを前提とする
- テストの追加・強化は既存の公開インターフェース（CLI のオプション、環境変数、出力形式、終了コード）を変更しない。唯一の例外は、検出済みの不具合の最小修正に伴うエラー出力（FR-023 の `--output` 書き込み失敗メッセージ、FR-025 の空指示の拒否）であり、いずれも終了コードの契約（0 / 1 / 2）を変えない
