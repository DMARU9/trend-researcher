**プロンプト工学の型**

| # | 工夫 | 実測（参照実装） | 何を解決するか |
|---|------|------------------|----------------|
| G1 | 停止条件を検出可能にする | 「Stop Immediately When: your last 2 searches returned similar information」（`prompts.py` の `research_system_prompt`） | 「十分なら止めよ」ではなく機械が判定できる条件で止める |
| G2 | 判断を算術に落とす | 「Simple queries: 2-3 search tool calls maximum / Complex: up to 5」 | 曖昧な「適切に」を排除 |
| G3 | 分岐の実例化 | `<Scaling Rules>`「top 10 リスト→1」「A vs B vs C の比較→3」「重複しない部分課題に委譲せよ」 | 委譲の粒度と重複回避を例で固定 |
| G4 | 構造を否定して自由度を与える | 「Section is a VERY fluid and loose concept」＋質問タイプ別に 4 つの構造例（比較 / 列挙 / 要約 / 単一回答）（`final_report_generation_prompt`） | テンプレートへの機械的流し込みを防ぐ |
| G5 | 重要指示を 2 つの役割で繰り返す | system に「verbatim で保持」＋直後の human に「DO NOT summarize… I want the raw information」（`compress_research_simple_human_message`） | 直近のユーザー発話を強く追う性質を利用 |
| G6 | 出力形式と引用番号の固定 | `<Output Format>` 3 節固定、`<Citation Rules>`「番号は欠番なく連番」＋具体例、抜粋は最大 5 件 | 引用番号の乱れを書式仕様で潰す |
| G7 | ドメイン別の要約方針 | ニュース=who/what/when、科学=手法・結果・結論、意見=論点、製品=仕様。「原文の 25〜30%」（`summarize_webpage_prompt`） | 素材の種類ごとに残す情報を変える |
| G8 | 空想の禁止と未指定の区別 | 「Fill in Unstated But Necessary Dimensions as Open-Ended」と「Avoid Unwarranted Assumptions」を別項目に（`transform_messages_into_research_topic_prompt`） | 「必要なのに未指定」と「単に未提供」を混同しない |
| G9 | 出典の選好 | 製品→公式/一次、学術→原著（サーベイ除外）、人物→本人ページ、言語→クエリ言語に一致 | 検索の質をプロンプト側で底上げ |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 長い素材のネタを取りこぼさない (Priority: P1)

利用者が「長い動画の内容を参考にしたい」と指示する。対象の動画は 1 時間あり、字幕は数万字に達する。現状は解析に渡す素材の先頭 20,000 文字だけが使われ、残りは無言で捨てられるため、後半で語られた具体例や失敗談がレポートに現れない。本機能では、素材全体を「情報を失わせない」方針で圧縮してから解析に渡すため、素材の後半にしか無いネタもレポートに載る。

**Why this priority**: レポートの価値は「素材からどれだけネタを拾えたか」で決まる。取りこぼしは利用者が気づけない形の品質劣化であり、最優先で解消する。

**Independent Test**: しきい値を超える素材（後半にのみ固有キーワードを含む）を入力し、解析に渡された入力とレポートにそのキーワードが現れることを確認する。圧縮を失敗させるモックを注入し、実行が完走して生素材が代替に使われることも確認する。

**Acceptance Scenarios**:

1. **Given** しきい値を超える素材、**When** 解析を実行する、**Then** 素材全体が圧縮を経て解析入力に反映され、後半にのみ現れるキーワードが結果に含まれる
2. **Given** しきい値以下の素材、**When** 解析を実行する、**Then** 追加の LLM 呼び出しは 0 回で、素材はそのまま解析に渡される
3. **Given** 圧縮が例外またはタイムアウトで失敗する、**When** 解析を実行する、**Then** 実行は完走し、生素材が使われたことと失敗の理由が進捗または注記に現れる
4. **Given** 素材長がしきい値を大きく超える、**When** 解析を実行する、**Then** モデルへ渡されたプロンプトの素材部分はしきい値以下に収まる

### User Story 2 - LLM の応答が崩れても動き続ける (Priority: P1)

利用者はモデルや接続先を差し替えて実行する。応答の書式はモデルごとに揺れ、現状は Markdown の見出しや表を正規表現で解析しているため、少し崩れると要約が空になるか、実行そのものが失敗する。本機能では、応答を構造化スキーマとして受け取り、取得に失敗したら規定回数まで自動再試行し、それでも得られなければ既存の決定的パーサへフォールバックする。

**Why this priority**: 「同じ指示を出せば同じ形で処理が進む」ことはパイプラインの前提である。応答の揺れがそのまま実行の成否になる状態を解消する。

**Independent Test**: スキーマに合致しない応答を返すモックで再試行回数と最終結果を確認し、全回失敗するモックで決定的パーサの経路へ落ちて実行が完走することを確認する。

**Acceptance Scenarios**:

1. **Given** 1 回目がスキーマ違反・2 回目が正常な応答、**When** 解析を実行する、**Then** 再試行により正常な応答が採用され、実行は成功する
2. **Given** 常にスキーマ違反の応答、**When** 解析を実行する、**Then** 規定回数で打ち切り、決定的パーサの経路で処理が継続する
3. **Given** LLM が一時的なエラー（ネットワーク・レート制限）を返す、**When** 解析を実行する、**Then** 規定回数まで再試行し、回復した場合は成功として扱う
4. **Given** 利用者の指示が英語、**When** 最終レポートを生成する、**Then** レポートは英語で出力される

### User Story 3 - 入力が上限に達しても最後まで走り切る (Priority: P2)

解析対象が多く素材も長い実行では、途中でモデルのコンテキスト長上限に当たる。現状は上限超過の例外がそのまま実行全体を失敗させる。本機能では、上限超過を検出し、入力を段階的に縮小して再試行する。縮退が起きたことは実行後に確認できる。

**Why this priority**: 実運用で最も起きやすい失敗であり、利用者にとっては「何も得られない」結果になる。ただし素材の圧縮（User Story 1）で大半は回避できるため、優先度は P2 とする。

**Independent Test**: コンテキスト長超過を返すモックを注入し、段階的な縮小を経て最終レポートが生成され終了コード 0 になることを確認する。

**Acceptance Scenarios**:

1. **Given** 上限超過を返すモデル、**When** 最終レポートを生成する、**Then** 入力が段階的に縮小され、規定回数内でレポートが生成される
2. **Given** 縮退が 2 回発生する、**When** 実行を完了する、**Then** 縮退の発生と縮小後の上限が進捗または注記に現れる
3. **Given** 上限超過以外のエラー（認証失敗など）、**When** 実行する、**Then** 上限超過と誤認して縮退せず、エラーとして終了コード 1 で終わる

### User Story 4 - 1 件の失敗でレポート全体を失わない (Priority: P2)

解析対象の一部で LLM が失敗する（レート制限、素材の破損、極端に長い 1 件など）。現状は 1 件の例外が実行全体を落とすため、正常に解析できた対象の結果も失われる。本機能では、失敗を 1 件単位で隔離し、成功分のレポートを生成する。失敗した対象は「解析できなかった」ことが分かる形でレポートに残る。

**Why this priority**: 取得できる素材は外部サービスに依存し、失敗をゼロにはできない。部分成功を返せることが実用性の下限を決める。

**Independent Test**: 解析対象 N 件のうち一部で例外を発生させるモックを注入し、成功分の結果がレポートに含まれ、失敗件数が明示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 解析対象 10 件のうち 3 件で恒久的な失敗、**When** 実行する、**Then** 7 件の解析結果を含むレポートが生成され、終了コードは 0
2. **Given** 解析対象の 1 件で素材が空、**When** 実行する、**Then** その対象は縮退した結果として扱われ、他の対象の解析は影響を受けない
3. **Given** 全ての解析対象で失敗、**When** 実行する、**Then** 実行は完走し、失敗の事実と理由が注記に現れる
4. **Given** 文脈取得が一部失敗する、**When** 実行する、**Then** 取得できた範囲で解析が行われ、レポートが生成される

---

### User Story 5 - 実行の予算と状態の行き先が分かる (Priority: P3)

利用者は「どこでどれだけの入力を扱ったか」「上限に当たったか」を実行後に確認したい。また、並列数や再試行回数を環境ごとに調整したい。本機能では、上限・しきい値・タイムアウトをすべて実行時設定から注入できるようにし、生データと整形済みデータを状態上で区別し、後続で不要になった大量の中間データを解放する。

**Why this priority**: 予算の管理そのものは品質を直接上げないが、調整できないと環境（レート制限・モデルの上限）に合わせられない。User Story 1〜4 が定めた上限を外から制御できるようにする仕上げとして位置づける。

**Independent Test**: 各設定を実行時に変更して挙動が変わることを確認し、設定の解決経路が 1 つであることと、不要になった中間データが状態から解放されることをテストで固定する。

**Acceptance Scenarios**:

1. **Given** 並列数・再試行回数・しきい値・タイムアウトを実行時設定で変更、**When** 実行する、**Then** 変更した上限が観測できる形で適用される
2. **Given** 環境変数と実行時指定が食い違う、**When** 実行する、**Then** 既定の優先順位に従って一方に確定し、両者が混ざらない
3. **Given** 実行が完了する、**When** 中間成果物を確認する、**Then** レポート確定後に不要となった生素材が状態に残っていない
4. **Given** 解析段の後続（共通テーマ抽出）、**When** 処理する、**Then** 生素材ではなく整形済みの解析結果のみを参照している

### User Story 6 - レポートの良し悪しを数字で比べられる (Priority: P1)

利用者はモデルやプロンプトを差し替えて「良くなったのか」を知りたい。現状は 547 件のテストが通るかどうかしか分からず、レポートの中身が良くなったかは読んで確かめるしかない。本機能では、**固定した指示セット**に対してレポートを複数の観点で採点し、2 つの構成を**提示順を伏せて**比較し、消費トークンと並べて記録する。結果は設定と入力の識別子に紐づけて保存するため、後から同じ条件で再現できる。

**Why this priority**: 「良くなったか分からないまま変更する」状態が最も危険である。改善の判断材料が無いと、User Story 1〜5 の変更が当て推量になる。対象に存在しない最大の欠落なので最優先とする。

**Independent Test**: 固定の指示セットとモックの判定モデルで採点が行われ、観点ごとの点数・理由・使用量・設定の識別子を含む結果ファイルが出力されることを確認する。判定モデルを失敗させ、実行が完走して失敗が記録されることも確認する。

**Acceptance Scenarios**:

1. **Given** 固定の指示セット、**When** 評価を実行する、**Then** 各レポートが複数の観点で採点され、観点ごとの点数と理由が記録される
2. **Given** 2 つの構成（例: 自己点検あり／なし）、**When** 比較評価を実行する、**Then** 提示順がランダム化され、順序に依存しない比較結果が得られる
3. **Given** プロンプトが課す制約（例: 出力言語・件数・引用形式）、**When** その制約に違反したレポートを評価する、**Then** 対応する観点で減点される（プロンプトの指示と評価項目が一致している）
4. **Given** 評価を実行する、**When** 結果を保存する、**Then** 実行時の設定・入力フィクスチャ・対象コミットの識別子が結果に含まれ、同じ条件で再実行できる
5. **Given** 通常のテスト実行（`uv run pytest -q`）、**When** スイートを実行する、**Then** 評価の実走は含まれず、ネットワークなしで完走する

---

### User Story 7 - 検索クエリを自分で点検してから実行する (Priority: P2)

X の検索は「5 件ちょうど」のクエリを前提にしているが、現状は LLM が一度出した案をそのまま使うため、似たクエリが並んだり、トピックの側面が抜けたりする。本機能では、生成直後に同じノード内で 1 回だけ自己点検を行い、重複の除去・不足の補充・期間表現の混入の除去をしてから確定する。点検が失敗しても生成結果で継続する。

**Why this priority**: クエリの質はレポートの網羅性を直接左右する。ただし既存の決定的な後処理（`_clean_query`）が安全網として残るため、P2 とする。

**Independent Test**: 生成 1 回＋点検 1 回の計 2 回で LLM 呼び出しが固定されること、点検で重複が除かれること、点検を失敗させても生成結果で同じ経路を進むことを確認する。

**Acceptance Scenarios**:

1. **Given** 生成結果に重複したクエリ、**When** 点検を行う、**Then** 重複が除かれ、規定件数に満たない分は補充される
2. **Given** 点検が例外・タイムアウトまたは空応答、**When** 実行する、**Then** 生成結果がそのまま使われ、実行は継続する
3. **Given** X プラットフォーム、**When** クエリを確定する、**Then** 5 件ちょうど（YouTube は 1 件）
4. **Given** 実行、**When** LLM 呼び出し回数を数える、**Then** 生成と点検の合計が固定回数を超えない（反復しない）
5. **Given** 自己点検の切り替えを無効にした実行、**When** クエリを確定する、**Then** 生成 1 回のみで確定し、クエリの件数の契約（X は 5 件、YouTube は 1 件）は有効時と変わらない

---

### User Story 8 - 実行コストと調整できる値が見える (Priority: P3)

利用者は実行ごとのトークン消費を知りたい。また並列数や上限を環境に合わせて調整したい。本機能では、LLM 呼び出しの使用量を実行 1 回単位で集計して記録し、実行時設定の各項目に型・値域・選択肢・既定値を宣言して Studio から調整できるようにする。

**Why this priority**: 品質改善の判断（User Story 6）にはコストが並んでいる必要があり、堅牢性の仕組み（User Story 1〜5）の上限は環境に合わせて調整できる必要がある。仕上げとして位置づける。

**Independent Test**: 集計値が中間成果物と進捗に現れること、宣言した値域外の値が起動時に拒否されること（終了コード 2）、Studio の `configurable` から変更できることを確認する。

**Acceptance Scenarios**:

1. **Given** 実行、**When** 完了する、**Then** 入力・出力トークンと呼び出し回数の集計が記録される
2. **Given** 値域を宣言した項目に範囲外の値、**When** 実行する、**Then** ノードの実行を開始する前に拒否され、項目名・与えられた値・期待する値域が示されて終了コード 2 で終わる（範囲外の値がそのまま適用されず、黙って別の値に置き換わることもない）
3. **Given** Studio の設定入力、**When** 並列数を変更する、**Then** 宣言した値域内で変更が反映される
4. **Given** 既存のレポート形式、**When** 集計を追加する、**Then** レポートの既存フィールドは削除・改名されない

---

### Edge Cases

各状況でシステムがどう振る舞うべきかを、対応する要件とともに固定する。

| 状況 | 期待する挙動 | 対応する要件 |
|------|--------------|--------------|
| 素材がしきい値ちょうど | 追加呼び出しを行わず生素材を使う（発動条件は「超えた場合」） | FR-001 / FR-008 |
| 素材がしきい値を 1 文字超える | 圧縮を実行する | FR-001 |
| 圧縮の応答が空文字 | 圧縮の失敗として扱い、生素材へ切り替える（空の結果を採用しない） | FR-003 |
| 圧縮がタイムアウト | 実行を停止せず生素材で継続し、失敗を記録する | FR-003 / FR-004 |
| 素材が空・本文なし（メタデータのみ） | 既存どおり縮退した要約を返し、実行は継続する | FR-020 / FR-021 |
| 解析対象が 0 件（検索結果なし） | 解析・共通テーマ抽出を実行せず、既存どおりレポートを生成する（挙動を変えない） | FR-030 / FR-034 |
| 縮退で入力を削っても上限超過が続く | 規定回数まで段階的に縮小し、使い切ったら理由を明示して終了コード 1 で終わる | FR-015 |
| 縮退で削る入力がもう残っていない | 上限超過として失敗を確定し、理由を明示する（無限ループにしない） | FR-015 |
| 解析対象が 1 件のみで、それが失敗 | 実行は完走し、成功 0 件・失敗 1 件としてレポートに明示される | FR-020 / FR-021 / FR-023 |
| 実行時設定の並列数に 0 や負値 | 起動時に拒否して終了コード 2 で終わる。無制限並列にも停止にもならない（丸めない） | FR-024 / FR-059 |
| 実行時設定の再試行回数に 0 | 再試行せず 1 回で確定し、失敗なら決定的パーサへフォールバックする | FR-010 / FR-011 / FR-024 |
| しきい値に素材長より極端に小さい値（例: 100 文字） | 指定どおり圧縮が発動し、圧縮失敗時は生素材で継続する（設定が意図どおり効く） | FR-003 / FR-005 |
| 再試行中に一時エラーとスキーマ違反が交互に発生 | 合計の試行回数が上限を超えない。使い切ったら打ち切ってフォールバックする | FR-010 / FR-011 |
| フォールバックでも解析結果が得られない | その対象を「解析できなかった」として記録し、実行は継続する | FR-021 / FR-023 |
| 進捗表示の総数・表示番号 | ノード構成を変えないため従来どおり一致する | FR-031 |
| 評価の判定モデルが失敗・空応答 | その観点を「採点できず」として記録し、他の観点の採点は継続する | FR-039 / FR-044 |
| 評価対象のレポートが空 | 採点せず「生成失敗」として記録する | FR-039 |
| 比較評価で片方のレポートが空 | 比較不能として記録し、勝敗を付けない | FR-041 |
| 比較評価で両方の提示順を入れ替えても差が無い | 引き分けとして記録する（差異が無いことを消さない） | FR-041 |
| 比較の指定した結果ファイルの一方が存在しない | 比較を開始せず、不足している対象を名指しして終了する（存在する片方だけで勝敗を付けない） | FR-041 / FR-072 |
| 比較の 2 件が別のデータセットの結果 | 比較不能として拒否する（同じデータセットと判定モデルで測った結果のみを比べる） | FR-041 / FR-072 / FR-073 |
| 評価の結果ファイルが既存と同じ名前 | 既存を消さず別名で保存し、実行の識別子で区別する | FR-043 |
| 自己点検が生成結果より少ない件数を返す | 規定件数に満たない分を補充し、契約件数を守る | FR-052 |
| 自己点検が空配列を返す | 生成結果をそのまま採用する（空のクエリ集合にしない） | FR-051 / FR-052 |
| 自己点検が上限を超える件数を返す | 既存の切り詰めに従う（上限を超えて検索しない） | FR-052 |
| 自己点検と生成が同じクエリを返す | 点検は差分なしと判断し、生成結果をそのまま採用する | FR-049 |
| 自己点検の切り替えが無効 | 生成 1 回で確定し、点検を行わない（呼び出しが 1 回減る）。クエリ件数の契約は変わらない | FR-054 / SC-036 |
| 自己点検の切り替え項目と中間データの切り替え項目を同時に指定 | 完全に独立した項目として扱う（片方を有効にしても他方の挙動は変わらない） | FR-046 / FR-054 |
| 応答に使用量（usage）が含まれない（プロキシが返さない） | 集計を「不明」として記録し、実行は継続する | FR-061 |
| 値域を宣言した設定に型違い（文字列など）を渡す | 起動時に拒否して終了コード 2 で終わる（既定値へ置き換えない・丸めない） | FR-059 |
| 既存フィールドに値域を新たに宣言し、従来は受理していた値が範囲外になる | 受理条件が狭まる変更として扱い、終了コード 2 の範囲内（引数エラー）で拒否する。既存テストの期待値は書き換えない | FR-059 / FR-035 |
| プロンプトの制約に対応する評価観点が無い | 対応表の更新を欠落として扱う（評価項目を先に足す） | FR-048 |
| 実走の入口が自動テストに収集される | 収集される命名規約に従わないことで担保する（収集設定は変えない） | FR-066 |
| 実走の実行時に判定モデルの資格情報が無い | 実行を開始する前に不足を明示して終了し、途中まで採点した結果を確定扱いにしない | FR-045 / FR-065 |
| 中間データの設定が既定（無効） | 状態にも戻り値にも中間データを含めず、stdout・レポート・既存キーを変更前と一致させる | FR-046 / SC-026 |
| 中間データの設定を有効にした実行 | 戻り値に中間データが現れるが、stdout のレポートは変わらない | FR-046 / FR-030 |
| 評価結果の保存先が未作成 | ディレクトリを作成して保存する。作成・書き込みに失敗した場合は理由を明示して終了する | FR-043 |
| 評価結果の保存先が既定（`artifacts/eval/`） | 版管理の追跡対象外に保存される。結果はリポジトリに残らず、環境をまたいだ比較はできない | FR-043 / SC-027 |
| 評価結果のファイル名が既存と同名 | 既存を無断で上書きしない（実行の識別子で区別する） | FR-043 / SC-027 |
| 点数が値域外（例: 7）を返す | そのまま記録する（範囲検査を追加しない）。記録に残るため、集計時に気づける | FR-067 / SC-028 |
| 点数が整数でない（例: 文字列） | 構造化出力の取得失敗として扱い、その観点を未採点にする | FR-039 / FR-067 |
| 観点の一部が応答に欠けている | 構造化出力の必須項目の欠落として取得失敗にし、その観点を未採点にする | FR-039 / FR-067 |
| データセットの中身が前回と変わっている | 指紋の不一致として記録し、過去の結果と同一視しない（比較を保留する） | FR-073 / SC-032 |
| 外部のデータセット名を指定したが到達できない | 既定のローカルデータセットに切り替えず失敗を明示する（黙って別の指示セットで測らない） | FR-070 |
| 正解（参照出力）が無いのに「正しさ」を測ろうとする | 実行を止めるか対象外として記録する。正解なしに点数を付けない | FR-038 / FR-074 |
| 用いた観点とプロンプトの制約の対応が取れていない | 対応表の更新を欠落として扱う（測っていない制約を作らない） | FR-048 / FR-074 |
| 判定モデルの環境変数（`TR_EVAL_MODEL`）が未設定 | コード上の既定値を使う。実走は開始できる | FR-069 / SC-034 |
| 判定モデルとして生成と同じモデルしか利用できない | 同じモデルで採点し、その事実を結果レコードから判別できる（自己選好バイアスが入りうる） | FR-069 / SC-034 |
| 判定モデルが解決できない（未知のモデル名・接続失敗） | 採点を開始する前に不足と理由を明示して終了する。一部だけ採点した結果を確定扱いにしない | FR-069 / FR-065 |
| 実走でレポートを CLI の subprocess 経由で取ろうとする | 状態に到達できず中間データ（FR-046）を取得できない。公開 API を in-process で呼ぶ経路に限る | FR-065 / FR-046 |
| 実走の初期状態の組み立てが CLI と二重化する | 複製してよいのは最小の 3 項目（指示文 1 件 / `platform` / 明示時の件数）に限る。CLI の引数解釈は再実装しない | FR-065 / FR-063 |

## Requirements *(mandatory)*

### Functional Requirements

#### 取り込み量の管理（コンテキストの圧縮）

- **FR-001**: 素材テキストが既定のしきい値を超える場合、システムは素材**全体**を LLM で圧縮してから解析入力に用いる MUST。先頭のみを無言で切り捨ててはならない MUST NOT
- **FR-002**: 圧縮は「情報を失わせない」方針で行い、要約と重要抜粋を区別した構造として受け取る MUST。単純な短縮要約にしてはならない MUST NOT
- **FR-003**: 圧縮が失敗（例外・タイムアウト・空応答）した場合、システムは生素材を用いて処理を継続 MUST。失敗は進捗または注記に現れ MUST、実行を失敗させてはならない MUST NOT
- **FR-004**: 圧縮の呼び出しにはタイムアウトを設定 MUST。応答が返らない場合に実行全体が停止してはならない MUST NOT
- **FR-005**: しきい値とタイムアウトは実行時設定から注入できる MUST。コードに固定値を置いてはならない MUST NOT（既定値は設定型が持ってよい）
- **FR-006**: 素材のうち解析入力に反映された範囲と、圧縮が行われた事実は、実行後に確認できる MUST
- **FR-007**: 圧縮後、解析プロンプトに載る素材の文字数はしきい値以下に収まる MUST。判定はモデルへ渡されたプロンプト長で行う MUST
- **FR-008**: しきい値以下の素材については、追加の LLM 呼び出しを行ってはならない MUST NOT

#### LLM 応答の契約化（一定の動作）

- **FR-009**: 指示解釈・個別解析・共通テーマ抽出の各 LLM 呼び出しは、結果を構造化スキーマとして受け取る MUST。自由文をそのまま解析の唯一の経路としてはならない MUST NOT
- **FR-010**: LLM 呼び出し（構造化出力の取得を含む）は規定回数まで自動再試行する MUST。回数は実行時設定から注入できる MUST
- **FR-011**: 構造化出力が規定回数失敗した場合、システムは既存の決定的な解析関数（`tools/parse.py`）の経路にフォールバックして処理を継続 MUST
- **FR-012**: 構造化出力の正常系と、決定的パーサへのフォールバック経路の**両方**をテストで固定する MUST
- **FR-013**: プロンプトには、実行の上限・停止条件・従うべき出力形式を、機械的に区別できる形で明示する MUST
- **FR-014**: 最終レポートの出力言語は利用者の指示と同じ言語に揃える MUST。指示と異なる言語で出力してはならない MUST NOT

#### 上限超過時の完走（段階的縮退）

- **FR-015**: LLM がコンテキスト長超過で失敗した場合、システムはそれを検出し、入力を段階的に縮小して再試行 MUST。縮小可能な入力が残っている間は規定回数内での成功を試み MUST、規定回数を使い切った場合は「上限超過のため生成できなかった」ことを理由として明示し、終了コード 1 で終わる MUST（無限に縮小を繰り返してはならない MUST NOT）
- **FR-016**: 縮小は入力の一部（古い中間メッセージ・過剰な素材）を段階的に落とす MUST。全量を一度に捨ててはならない MUST NOT
- **FR-017**: 段階的縮退が発生した場合、その事実と縮小後の上限は実行後に確認できる MUST
- **FR-018**: 上限超過の検出は対象エンドポイント（OpenAI 互換）の応答から判定する MUST。判定できない失敗を上限超過と誤認してはならない MUST NOT
- **FR-019**: 素材の圧縮（FR-001）と段階的縮退（FR-015）は別の段階として扱い、両方が発生した場合も各段階の縮退が記録される MUST

#### 部分失敗の隔離

- **FR-020**: 解析対象の 1 件が失敗しても、その他の対象の解析を継続 MUST。1 件の失敗がレポート全体を失わせてはならない MUST NOT
- **FR-021**: 失敗した対象は、解析できなかったことが分かる形でレポートに残る MUST。無言で欠落させてはならない MUST NOT
- **FR-022**: 外部取得（検索・文脈取得）が一部失敗した場合、取得できた候補でレポートを生成 MUST
- **FR-023**: 解析の失敗件数とその理由は、実行後に確認できる MUST

#### 予算と状態のライフサイクル

- **FR-024**: 並列実行数・再試行回数・取り込みしきい値・タイムアウト・縮退回数は、すべて実行時設定の唯一の型から解決する MUST。ノードに数値をハードコードしてはならない MUST NOT（既定値は型が持つ）。不正な値（並列数・回数・タイムアウトに 0 以下、非数値）は**起動時に拒否**する MUST（値域外・型違いを既定値へ黙って置き換えたり値域へ丸めたりしてはならない MUST NOT。未設定（None）は既定値を使う）。拒否は項目名・与えられた値・期待する値域を明示して行い、ノードの実行を開始せず終了コード 2 で終わる MUST。無制限の並列実行や停止しない再試行に陥ってはならない MUST NOT
- **FR-025**: 実行時設定は 1 つの解決経路を持つ MUST。環境変数と実行時指定（CLI / Studio）で解決結果が食い違ってはならない MUST NOT
- **FR-026**: 生データ（取得した素材）と整形済みデータ（解析結果）を状態上で区別する MUST。整形済みデータのみを必要とする後続段は生データを参照してはならない MUST NOT
- **FR-027**: 後続段で不要になった大量の中間データは、状態から解放できる MUST
- **FR-028**: 実行の上限（並列数・再試行回数・縮退回数）は、実行 1 回あたりの上限としてテストで固定する MUST
- **FR-029**: 進捗表示には、各段の入力量と縮退の有無が現れる MUST

#### 契約の維持とスコープ

- **FR-030**: CLI の観測可能な契約（終了コード 0/1/2、stdout はレポートのみ、stderr は進捗とエラー）を維持 MUST
- **FR-031**: 7 ノードの構成と進捗表示の総数を維持 MUST。参照実装のアーキテクチャ（上位エージェントによる動的な委譲・並列サブリサーチャーの階層・反復ループ）を取り込んではならない MUST NOT
- **FR-032**: 長文素材の圧縮に伴う追加の LLM 呼び出しは、しきい値を超えた素材に限る MUST
- **FR-033**: 新しい実行時依存を追加してはならない MUST NOT。取り込みは既存の依存（LangGraph / LangChain / Pydantic）の範囲で実現する MUST
- **FR-034**: 既存のレポート形式（Markdown / JSON）のフィールドを削除・改名してはならない MUST NOT（追加は可）
- **FR-035**: 観測可能な振る舞いを固定する既存テストは、期待値を書き換えることなく green を維持 MUST。失敗した場合はテストではなくソースを修正 MUST
- **FR-036**: テストスイートはネットワークと実認証情報なしで完走 MUST
- **FR-037**: 参照実装から取り込む工夫は、本リポジトリの provider 境界と原則（テスト必須・型付き契約・プラットフォーム抽象）に適合する形で実装する MUST。参照実装のコードをそのまま複製してはならない MUST NOT

#### 品質の測定（評価基盤）

- **FR-038**: レポートの品質を**複数の観点**で採点する評価基盤を持つ MUST。観点は参照実装の 6 評価（総合品質・関連性・構造・正しさ・根拠性・網羅性。`tests/evaluators.py`）を基盤とし MUST、少なくとも「総合品質」「関連性」「構造」「根拠性」「網羅性」の 5 つを採点する MUST。「総合品質」は 6 つの下位の基準（調査の深さ・情報源の質・分析の厳密さ・実用的価値・中立性と客観性・文章の質）の点数として記録する MUST。参照出力（正解）を必要とする「正しさ」は、正解を用意できない場合に**対象外であることを明示**する MUST（採点結果から黙って落として欠落を隠してはならない MUST NOT）。「出力言語の一致」など対象固有の観点は追加してよく MUST、追加した観点も FR-039 の形（識別子・点数・理由）を保つ MUST
- **FR-039**: 採点は構造化スキーマ（型付きモデル）で受け取り、観点ごとに「識別子・点数・理由」の組の一覧として記録する MUST。点数は 1〜5 の整数として受け取り、0〜1 に正規化して記録する MUST。点数だけを記録し、なぜその点かを残さない状態にしてはならない MUST NOT（参照実装は 6 観点中 5 観点が `reasoning` を必須項目に持ち、`score / 5` で正規化する）
- **FR-040**: 各観点には専用の判定プロンプトを対応させ、判定プロンプトは生成側のプロンプトが課す制約を反映する MUST（参照実装は観点ごとの判定プロンプトを持ち、生成側の指示を評価基準に取り込む。`tests/prompts.py`）
- **FR-041**: 2 つ以上の構成を比較する評価は、**提示順をランダム化**して行う MUST（順序効果を結果に持ち込まない MUST）。比較は**構成ごとに独立に実行して保存した結果**を、名前で指定して行う MUST（1 回の実行で 2 構成を順に走らせる方式を唯一の経路としてはならない MUST NOT。判定のみをやり直せることを優先する）。生成の実行回数は構成ごとに 1 回とし MUST、判定の再実行のために生成をやり直すことを強制してはならない MUST NOT（参照実装は `evaluate_comparative((実験A, 実験B), evaluators=[...], randomize_order=True)` に実験名のタプルを渡し、生成と比較を分離している。`tests/pairwise_evaluation.py:124-128`）。比較の判定は、勝敗を付ける観点（どちらを選好するか）と、勝敗を付けない結果（どちらも選ばない）を区別して記録する MUST
- **FR-042**: 評価は品質の点数に加えて、実行 1 回あたりのトークン数と呼び出し回数を併せて記録する MUST。品質とコストを並べて比較できる MUST
- **FR-043**: 評価結果は、実行時の設定・入力フィクスチャ・対象コミットの識別子・**判定に用いたモデル名**とともに保存する MUST。同じ条件で再実行でき、結果を比較できる MUST。保存形式は 1 行 1 レコードの機械可読な形式（JSONL）とし MUST、保存先のディレクトリを作成し、保存先と件数を実行後に知らせる MUST。既定の保存先はリポジトリの成果物置き場（`artifacts/eval/`）とし MUST、この置き場を版管理の追跡対象に含めてはならない MUST NOT（結果はリポジトリに残さない）。保存先は引数または環境変数で変更できる MUST
- **FR-044**: 評価の実走（LLM 呼び出しを伴う部分）をテストスイートの合否条件に含めてはならない MUST NOT。テストで固定するのは判定ロジック・採点スキーマの解釈・プロンプトと評価項目の対応である MUST
- **FR-045**: 評価基盤は既存の依存と既存の LLM 構築経路（`tools/llm.py`）の範囲で実装する MUST。評価専用のライブラリを必要とする場合は**開発用の追加依存**に限定し、実行時依存に含めてはならない MUST NOT。外部の評価サービスのアカウントを必須としてはならない MUST NOT（参照実装は評価専用の依存を `[project.optional-dependencies]` に隔離している。`pyproject.toml:17, 39`）。判定（採点）に用いるモデルも同じ構築経路（`tools/llm.py`）で構築する MUST。`ChatOpenAI` 等を直接構築して対象の接続設定（`OPENAI_BASE_URL` と `x-opencode-session` ヘッダー）を迂回してはならない MUST NOT（参照実装は `tests/evaluators.py:8-10` で `ChatOpenAI(model="gpt-4.1")` を直に構築しており、この点は真似しない）
- **FR-046**: 中間データ（採用したクエリ・素材長・解析件数・縮退や失敗の発生）の出力は、**出荷される設定クラスの boolean 項目（既定は無効）** で切り替える MUST。当該項目が無効のとき、状態と戻り値に中間データを含めてはならず、既存の出力（stdout のレポート・レポートファイル・戻り値の既存キー）が変化してはならない MUST NOT。有効にしたときのみ中間データを状態と戻り値に含める MUST。評価の実走はこの項目を有効にして実行する MUST
- **FR-047**: 運用特性（並列度・上限の遵守・縮退の発生）を測定で検証する評価項目を持つ MUST。プロンプトの記述のみで満たされたと見なしてはならない MUST NOT
- **FR-048**: プロンプトが課す制約と評価基盤が採点する観点を対応させ、対応表を保つ MUST。制約を書いたままそれを測らない状態を作ってはならない MUST NOT

#### 検索クエリの自己点検

- **FR-049**: 検索クエリの生成後、**同一ノード内で 1 回**の自己点検を行う MUST。点検は重複の除去・不足の補充・期間表現の混入の除去を対象とする MUST
- **FR-050**: 自己点検の呼び出し回数は **1 回に固定**する MUST。条件を満たすまで点検を繰り返す反復ループにしてはならない MUST NOT
- **FR-051**: 自己点検が失敗（例外・タイムアウト・空応答）した場合、生成結果をそのまま用いて処理を継続する MUST。点検の失敗で実行を落としてもならない MUST NOT
- **FR-052**: 点検後のクエリは provider の契約（プラットフォームごとの規定件数と上限）を満たす MUST
- **FR-053**: 自己点検の追加分（呼び出し回数）をテストで固定する MUST。自己点検が有効なとき、生成と点検の合計が実行 1 回あたりの上限（生成 1 回＋点検 1 回）を超えない MUST
- **FR-054**: 自己点検の実行は実行時設定の**真偽値（boolean）項目**で切り替えられる MUST（既定は有効）。**出荷される設定クラス（`Configuration`）の項目として 1 つ追加する** MUST（参照実装の `include_source_str` と同じ形。`legacy/configuration.py:42, 78`）。無効にした場合は生成の 1 回で確定し MUST、点検の判断をそのとき行ってはならない MUST NOT（無効時の呼び出しは生成 1 回のみ）。有効・無効のいずれでもクエリ件数の契約（FR-052）を満たす MUST。この項目は**評価の比較のための構成差**を作る手段であり、評価専用の仕組みを別に設けない MUST（`FR-047` の観点を他の設定差と同じ手順で測れる MUST）

#### プロンプトの深化

- **FR-055**: 各プロンプトには、機械が判定できる停止条件を明示する MUST（例: 直近 2 回の取得結果が同種なら打ち切る）
- **FR-056**: 停止条件を「適切に」「必要なら」のような判定不能な表現のみで示してはならない MUST NOT
- **FR-057**: 出力構造は固定テンプレートで与えず、指示の種類ごとの構造の例を示す MUST
- **FR-058**: 重要な制約（出力言語・件数・引用形式）は、役割の異なる 2 箇所で明示する MUST

#### 設定の宣言と使用量の計測

- **FR-059**: 実行時設定の各項目は、型・値域・選択肢・既定値・説明を宣言する MUST。値域を宣言した項目は、値域外の値と型違いを**起動時に拒否**する MUST。丸め（クランプ）や既定値への置き換えを行ってはならない MUST NOT（置き換えた事実を警告で知らせる運用も採用しない）。未設定（None）は既定値を使う MUST。拒否の際は項目名・与えられた値・期待する値域を示し、ノードの実行を開始せず終了コード 2 で終わる MUST
- **FR-060**: 実行時設定は Studio（`configurable`）から変更できる MUST。宣言した値域がその入力の契約となる MUST（解決経路は FR-025 の単一経路を維持する MUST）
- **FR-061**: LLM 呼び出しの使用量（入力・出力トークン、呼び出し回数）を実行 1 回単位で集計する MUST。使用量が応答に含まれない場合は「不明」として記録し、実行を失敗させてはならない MUST NOT
- **FR-062**: 集計結果は中間成果物と進捗に記録する MUST（レポート形式の扱いは FR-034 に従う）

#### 移植の統制

- **FR-063**: 参照実装の実測済みの欠陥（常に真の条件分岐による例外の握りつぶし・無効なオプション指定・到達不能コード・プロバイダ固有の例外型への依存・部分文字列によるモデル判定・ツール契約の非対称）を移植してはならない MUST NOT
- **FR-064**: 上限超過の検出（FR-018）の設計は、対象エンドポイントが実際に返す応答（例外の型・メッセージ・本文）を実測した結果に基づく MUST。参照実装の判定条件をそのまま用いてはならない MUST NOT

#### 評価基盤の配置（実走の入口）

- **FR-065**: 評価の実走（LLM 呼び出しを伴う手動の確認）の入口は、既存 CLI とは別の**独立したスクリプト**として提供する MUST。既存 CLI の引数契約（`instruction` が必須の位置引数であること、`--platform` の必須性、既存オプションの受理と拒否）を変更してはならない MUST NOT。評価用の依存やコードを出荷パッケージの経路に含めてはならない MUST NOT。実走は出荷パッケージの公開 API を **in-process** で呼んで駆動する MUST（`trend_researcher.ainvoke(initial_state, runnable_config)` の戻り値（状態）から最終レポートを得て `render_report()` で文字列化する）。CLI を subprocess として起動し stdout からレポートを取得する方式を採ってはならない MUST NOT（中間データは戻り値にしか現れず、FR-046 の観点を取り出せないため）。初期状態の組み立ては実走スクリプト側に持ち MUST、複製してよいのは CLI と同じ最小の項目（`messages` = 指示文 1 件 / `platform` / 明示指定時の件数）に限る MUST。CLI の引数解釈（`--since` などの正規化）を再実装してはならない MUST NOT
- **FR-066**: 実走の入口は自動テストの収集対象に含めてはならない MUST（収集される命名規約に従わない）。また既存のテスト収集の設定（`testpaths`）を変更してはならない MUST NOT。実走に必要な値（対象プラットフォーム・フィクスチャの場所・結果の保存先・**判定に用いるモデル**）は、引数または環境変数で与える MUST
- **FR-067**: 点数の値域の検査は構造化スキーマの記述に委ね、追加の範囲検査を設けない MUST（参照実装は `int` 型と「Integer score 1-5」の説明のみで、`ge` / `le` 等の制約を置いていない。`tests/evaluators.py:26-39`）。範囲外の点数が返った場合はそのまま記録し MUST、評価の実行を止めてはならない MUST NOT。型違い・必須項目の欠落は構造化出力の取得失敗として扱う MUST
- **FR-068**: 判定の再試行の規則はすべての観点で同一とする MUST。観点によって再試行の有無を変えてはならない MUST NOT（参照実装は根拠性の評価器にのみ `with_retry(stop_after_attempt=3)` を付けているが、この非対称は移植しない。FR-063 の趣旨）
- **FR-069**: 判定（採点）に用いるモデルは、生成に用いるモデルと**別に**指定できる MUST。参照実装は判定モデルをモジュール定数に直書きしている（`tests/evaluators.py:8-10` の `eval_model = ChatOpenAI(model="gpt-4.1")`）が、対象は `.env` / 環境変数（`TR_EVAL_MODEL`）で指定する MUST。解決は既存の規則（`resolve_env("EVAL_MODEL", default=...)` の `TR_{name}` → `{env_prefix}_{name}` → 既定）に従う MUST。既定値はコードに持ち MUST、生成に用いるモデルとは異なるモデルとする SHOULD（同じモデルで採点すると自己選好バイアスが入る）。ただし利用可能なモデルが 1 つしかない環境でも実走でき MUST、同じモデルで採点した場合はその事実を結果から判別できる MUST。**出荷する設定クラス（`Configuration`）に判定モデルの項目を追加してはならない MUST NOT**（判定は出荷物の実行経路ではなく、FR-066 のとおり実走の入口に属する値であるため）。実際に使用した判定モデル名は評価結果の設定識別子に含める MUST（FR-043）

#### 評価フィクスチャと記録の形（参照実装の構造に合わせる）

- **FR-070**: 評価対象の指示セットは**名前付きのデータセット**として指定する MUST（参照実装は `dataset_name = "Deep Research Bench"` のように名前で指定する。`tests/run_evaluate.py:14`）。データセットは**指標の集合を同一に保つ単位**であり、名前を変えると結果の比較対象が変わる MUST。既定のデータセットはリポジトリ内の固定ファイルとして持ち、外部サービスを必須としてはならない MUST NOT（FR-045 と両立させる）。外部のデータセットを名前で参照する経路は任意で設けてよい MUST（必須にしてはならない MUST NOT）
- **FR-071**: 評価結果のレコードの形は、指示文と生成された成果物を識別子で結ぶ最小の組とする MUST。参照実装は `{"id": ..., "prompt": ..., "article": ...}` の 3 項目を 1 行 1 レコードで書く（`tests/extract_langsmith_data.py:40-45`）。同じ形をとり MUST、採点結果は識別子で結び付けられる MUST
- **FR-072**: 結果ファイルの名前は**データセット名と対象の識別子を含む** MUST（参照実装は `tests/expt_results/{dataset_name}_{model_name}.jsonl`。`tests/extract_langsmith_data.py:50`）。これにより、異なるデータセットや構成の結果が混ざらず、`FR-043` の設定識別子と併せて比較対象が定まる MUST。比較の対象となる構成の違い（例: 自己点検あり / なし）は名前に現れる識別子で区別でき MUST、同名の結果が別の構成を指す状態を作ってはならない MUST NOT
- **FR-073**: データセットの識別子（名前と、可能なら内容の指紋）を評価結果に記録する MUST。指示セットの中身が変わった場合、過去の結果と同一視できないことが分かる MUST
- **FR-074**: 観点の一覧、プロンプトの制約との対応（FR-048）、および参照実装の 6 評価との対応（採用した観点・対象外とした観点とその理由）を**1 つの対応表**に記録する MUST。対象外とした観点がある場合、その観点が未測定であることを利用者が判別できる MUST

### Key Entities *(include if feature involves data)*

- **素材（ソーステキスト）**: 解析の入力となる生のテキスト（X のスレッド＋リプライ、YouTube の字幕）。長さが可変で、上限を超える場合は圧縮の対象になる
- **圧縮済み素材**: 素材全体を情報を失わせずに縮めた結果（要約と重要抜粋）。圧縮が失敗した場合は生素材がこの位置に入る（劣化として記録される）
- **構造化出力スキーマ**: 指示解釈・個別解析・共通テーマ抽出の各段で LLM から受け取る形の契約。取得に失敗した場合は既存の決定的パーサが代替する
- **実行予算**: 並列実行数・再試行回数・取り込みしきい値・タイムアウト・縮退回数。実行時設定の唯一の型が保持する
- **縮退の記録**: 圧縮の失敗、上限超過による縮小、解析できなかった対象の一覧。進捗または注記として利用者に現れる
- **生データと整形済みデータ**: 状態上で区別される 2 種類。後続段が参照してよいのは整形済みデータのみ
- **評価フィクスチャ**: 評価に用いる固定の指示セットと、それに対応する既知の参照。判定ロジックのテストにも同じフィクスチャを使う
- **評価結果**: 固定の指示セットに対する採点の記録。観点ごとの点数と理由、使用量、判定に用いたモデル名、実行時の設定・入力フィクスチャ・対象コミットの識別子を含む
- **クエリ案とその点検結果**: 検索クエリの生成結果と、それを点検した結果（除去・補充の内容）。点検が失敗した場合は生成結果がそのまま確定する
- **使用量の集計**: 実行 1 回あたりの入力・出力トークンと呼び出し回数。応答が使用量を返さない場合は「不明」として扱う
- **値域の宣言**: 実行時設定の各項目が持つ型・値域・選択肢・既定値。Studio の入力契約と検証の根拠になる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: しきい値（既定 20,000 文字）を超える素材（例: 60 分動画の字幕 ≈ 10 万文字）を与えたとき、素材全体が解析に反映される。判定は「前半に存在しないキーワード」が解析結果または中間成果物に現れることで行う（変更前: 先頭 20,000 文字のみ使用）
- **SC-002**: 素材長 10 万文字に対する解析プロンプトの素材部分の文字数がしきい値以下に収まる
- **SC-003**: しきい値以下の素材では、解析 1 件あたりの追加 LLM 呼び出しが 0 回である（呼び出し回数をモックで計測）
- **SC-004**: 圧縮が失敗（例外・タイムアウト・空応答）しても、実行は完走し終了コードが 0 になる。失敗の事実が進捗または注記に現れる
- **SC-005**: 構造化出力が契約に合わない応答を返した場合、規定回数（既定 3 回）まで再試行される。全回失敗した場合も決定的パーサの経路で処理が継続し、実行は失敗しない
- **SC-006**: 上限超過（コンテキスト長）を返すモデルを与えても、段階的な縮小により最終レポートが生成され、終了コードが 0 になる。縮小できる入力をすべて使い切っても成功しない場合に限り、理由を明示して終了コード 1 で終わり、縮小を無限に繰り返さない
- **SC-007**: 解析対象 10 件のうち 3 件が恒久的に失敗しても、残り 7 件の解析結果を含むレポートが生成される。失敗 3 件は「解析できなかった」ことが分かる形で残る
- **SC-008**: 実行 1 回あたりの同時 LLM 呼び出し数が上限（既定 2）を超えず、再試行回数が上限（既定 3）を超えないことがテストで固定されている
- **SC-009**: 取り込みしきい値・タイムアウト・並列数・再試行回数・縮退回数のすべてが実行時設定から変更できる。コード上の数値は既定値のみであり、設定の解決経路が 1 つ（環境変数と実行時指定が食い違った場合の優先順位もテストで固定）である。不正な値（0 以下・非数値）を与えた場合は起動時に拒否され（終了コード 2）、無制限の並列実行や停止しない再試行にはならない
- **SC-010**: レポート確定後、状態に生素材が残っていない。共通テーマ抽出の段は整形済みの解析結果のみを入力とする
- **SC-011**: 7 ノードの構成・進捗表示の総数・レポート形式（Markdown / JSON）が変更前と一致する
- **SC-012**: 利用者可視の契約（終了コード 0/1/2、stdout はレポートのみ、stderr は進捗とエラー、オプションの受理・拒否）がテストで固定されたまま green である
- **SC-013**: 品質ゲート 3 種（自動テスト・Lint・型チェック）がリポジトリ全体で green であり、テストスイートはネットワーク・実認証情報なしで 60 秒以内に完走する
- **SC-014**: 実行時依存の追加が 0 件である
- **SC-015**: 固定の指示セット（例: 5 件）に対して、各レポートが 5 観点以上で採点され、観点ごとの点数と理由を含む結果ファイルが出力される
- **SC-016**: 2 構成の比較評価で提示順がランダム化され、同じ入力に対して提示順を入れ替えても選好の向きが偏らない（順序効果の検証手順が結果に残る）。比較は構成ごとに独立に実行して保存した結果 2 件を名前で指定して行われ、生成をやり直さずに判定のみを再実行できる（生成の実行回数は構成ごとに 1 回）
- **SC-017**: 評価結果に、実行時の設定・入力フィクスチャ・対象コミットの識別子が含まれ、同じ条件で再実行して同じフィクスチャ集合を再現できる
- **SC-018**: 通常のテスト実行（`uv run pytest -q`）がネットワーク・実認証情報なしで完走し、評価の実走を含まない。判定ロジック・採点スキーマの解釈・プロンプトと評価項目の対応は固定されたテストで検証されている
- **SC-019**: 評価基盤の追加によって実行時依存が増えていない（0 件）
- **SC-020**: プロンプトが課す制約（出力言語・件数・引用形式・自己への言及の禁止など）と評価基盤の採点観点が対応表で対応している
- **SC-021**: 自己点検が有効なとき、検索クエリ生成の LLM 呼び出し回数が生成 1 回＋点検 1 回の 2 回で固定される（X / YouTube の両方）。点検を失敗させても実行が完走し、クエリ件数の契約（X は 5 件、YouTube は 1 件）が守られる。自己点検を無効にした場合は生成 1 回のみで同じ契約を満たし、呼び出しが 1 回減る
- **SC-022**: 実行 1 回あたりの入力・出力トークン数と呼び出し回数が中間成果物と進捗に現れる。エンドポイントが使用量を返さない場合も実行は完走し「不明」として記録される
- **SC-023**: 実行時設定の全項目に型・値域・選択肢・既定値が宣言され、値域外の値と型違いは起動時に拒否される（終了コード 2 で終わり、範囲外の値が適用も丸めもされない）。Studio の `configurable` から変更できる
- **SC-024**: 評価基盤により、自己点検あり／なしの 2 構成を比較した結果を、品質スコアとトークン数の組で提示できる（しきい値・上限・縮退の設定を変えた場合も同じ手順で比較できる）
- **SC-025**: 評価の実走の入口が既存 CLI とは別の独立スクリプトとして存在し、既存 CLI の引数契約が変更されていない（既存の観測可能テストが期待値の書換なしに green）。実走の入口は自動テストの収集対象に含まれず、`testpaths` の設定も変更されていない
- **SC-026**: 中間データを切り替える設定項目が既定で無効であり、無効時の実行結果（stdout のレポート・レポートファイル・戻り値の既存キー）が変更前と一致する。有効にしたときのみ中間データが状態と戻り値に現れ、stdout のレポートは変わらない
- **SC-027**: 評価結果が 1 行 1 レコードの JSONL としてディレクトリへ保存され、保存先と件数が実行後に分かる。既定の保存先は `artifacts/eval/` であり、版管理の追跡対象に含まれない（`.gitignore` の対象である）。既存の結果ファイルを無断で上書きしない
- **SC-028**: 各観点の点数が 1〜5 の整数として受け取られ 0〜1 に正規化されて記録される。判定モデルが値域外の点数を返した場合もそのまま記録され、評価の実行は中断しない。値域の追加検査を行っていない（範囲外の値で実行が止まらないことをテストで確認する）
- **SC-029**: 判定の再試行の規則が全観点で同一である（観点によって再試行の有無が異ならないことをテストで確認する）
- **SC-030**: 評価対象の指示セットが名前付きのデータセットとして指定でき、既定のデータセットがリポジトリ内の固定ファイルとして存在する。外部サービスのアカウントが無くても評価の実走を開始できる
- **SC-031**: 結果のレコードが「識別子・指示文・成果物」の 3 項目を持つ 1 行 1 レコードの形式であり、採点結果が識別子で結び付いている。結果ファイルの名前にデータセット名と対象の識別子が含まれる
- **SC-032**: データセットの名前と内容の指紋が評価結果に記録され、指示セットを変更した場合に過去の結果と同一視されないことが分かる
- **SC-033**: 参照実装の 6 評価との対応が 1 つの対応表に記録され、採用した観点と対象外とした観点（およびその理由）が分かる。対象外の観点は未測定であることが明示され、判定結果から黙って欠落していない（正解を要する「正しさ」を正解なしに測っていないことが確認できる）
- **SC-034**: 判定（採点）に用いるモデルが生成モデルとは別に `.env`（`TR_EVAL_MODEL`）で指定できる。未設定時はコード上の既定値が使われ、生成とは異なるモデルが既定である。判定モデルは出荷する設定クラス（`Configuration`）の項目としては現れない。同じモデルしか使えない場合でも実走でき、使用した判定モデル名が評価結果の設定識別子に記録されている
- **SC-035**: 実走の入口が公開 API（`trend_researcher`）を in-process で呼んでレポートを得ており、CLI の subprocess 起動を含まない（実走スクリプトの依存・コードに CLI の起動が現れない）。中間データを有効にした実行で、戻り値から採用クエリ・素材長・縮退の発生が取得できる
- **SC-036**: 自己点検の切り替えが実行時設定の真偽値項目（既定は有効）として宣言されており、無効にした実行では生成 1 回でクエリが確定して点検の判断が行われない。有効・無効のどちらでもクエリ件数の契約（X は 5 件、YouTube は 1 件）が守られる。この項目が「自己点検あり／なし」の比較の構成差を作り、評価専用の切り替え手段を別に持たないことが確認できる（この項目は FR-046 の中間データの切り替えとは独立である）

## Assumptions

- 取り込む対象は、参照実装が仕組みとして凝らしている工夫（C1〜C7 / D1〜D9 / E〜J のうち、**品質の測定・設定の宣言・使用量の計測・プロンプトの深化・自己点検**）とする。参照実装のアーキテクチャ（階層型エージェント構成・動的な委譲・反復ループ・利用者への確認ステップ）と、MCP 連携・配布形態は取り込まない（FR-031）。これらは別機能として、必要になった時点で設計する
- 長文素材の圧縮は、参照実装と同じ方針（しきい値超過時のみ）で行う。すべての素材を常に圧縮する運用は採用しない（SC-003）
- 対象は OpenAI 互換エンドポイントのみを前提とする。上限超過の判定はこの経路に限定し、他プロバイダ向けの判定は導入しない（YAGNI。原則 VI）
- 「情報を失わせない圧縮」は生成モデルの出力に依存するため、完全な情報保持は保証しない。保証するのは (a) 素材全体が入力に渡ること、(b) 抽出された要約・抜粋を通じて後半の内容が解析に届きうること、(c) 圧縮に失敗した場合に生素材へ戻ること
- 圧縮の出力形式は構造化スキーマ（要約＋重要抜粋）とする。既存の決定的パーサはフォールバックとして残す（FR-011）。正規表現による経路を削除するのではなく、正常系と異常系の両方をテストで固定する
- 上限超過の検出は例外の型とメッセージの照合で行う。誤検出（FR-018）を避けるため、上限超過以外のエラーは縮退させず、利用者に失敗として返す
- 段階的縮退で用いる「モデルの上限値」は、既知のモデル名から解決するテーブルを持つ。未知のモデルでは上限が不明であることを明示して終了する（黙って失敗しない）
- 実行時設定のフィールドは加算のみとする。既存フィールドの削除・改名を行わないことで、`cache/` の JSON 表現の後方互換を保つ（FR-034）
- 既存テストは、観測可能な振る舞いを固定しているものは変更せずに green を維持する。内部構造（関数のシグネチャ・フィールドの一覧・呼び出し回数）を固定しているテストは、追加・改名に伴い更新する。この区別と更新内容は実装時に記録する（FR-035）
- 進捗表示の総数と表示番号は単一の定義（`NODE_ORDER`）から導出する既存の仕組みを維持する（原則 V）。ノードの追加・削除を伴わないため、進捗表示の行数は変化しない
- 外部 I/O の境界（`tools/` と `providers/`）に圧縮・再試行・タイムアウトの実装を置き、ノードはその関数を呼ぶだけにする。テストは境界のモックで完走させる（原則 II）
- プロジェクト憲法（原則 I〜VI）を遵守する。特に原則 I（テスト必須）と原則 VI（互換シムを残さない）を前提とし、安全網は互換層ではなくテストで確保する
- 本仕様は既存の観測可能な挙動を変えないことを制約とする。レポートの形式・進捗の形式・CLI の契約は維持し、内部の処理の堅牢性と入力の扱い、および追加の評価基盤のみを変更する
- 評価基盤は本仕様に統合するが、**実走はテストスイートの合否条件から外す**（FR-044）。テストで固定するのは判定ロジック・採点スキーマの解釈・プロンプトと評価項目の対応であり、実走は README に記載する手動の確認とする。これにより原則 II（ネットワークなしで完走）を維持する
- 評価基盤は既存依存の範囲で実装し、外部の評価サービス（LangSmith 等）を必須にしない（FR-045）。結果はローカルの JSONL または JSON とし、外部リーダーボードへの提出は範囲外とする
- 判定（judge）モデルの妥当性（人の判断との一致）は本仕様の範囲外とする。範囲に含むのは、判定ロジックが固定のレポートと既知の期待値に対して期待どおり動くこと、採点結果が監査可能（点数＋理由）であること
- 自己点検は 1 回に限定する（FR-050）。反復ループ（条件を満たすまで点検を繰り返す）は導入しない。追加される LLM 呼び出し 1 回分の実行時間・コスト増は許容し、その効果は評価基盤で測る（利用者の判断）。
- 検索クエリの点検は既存の決定的な後処理を置き換えない。点検を通った後も既存の後処理を経由し、最終的な契約（件数・文字種）は既存の経路が保証する
- 使用量の集計は応答の usage 情報に依存する。OpenAI 互換プロキシが使用量を返さない場合は「不明」として記録し、実行を失敗させない（FR-061 / SC-022）
- 上限超過の検出条件（FR-018 / FR-064）は、対象エンドポイントが実際に返す応答を実測してから設計する。参照実装が依存する例外クラス名（`BadRequestError` 等）は移植しない
- 評価基盤の実装は `tests/` 配下の補助（判定ロジック・フィクスチャ・採点スキーマ）と、実走用の入口（`script/` 配下の独立スクリプト。既存の `script/analyze_structure.py` に倣う）に分ける。実走をテストの収集対象に混ぜない（FR-065 / FR-066）
- 中間データの出力は、参照実装の `include_source_str` と同じ形をとる（FR-046）。すなわち、**出荷される設定クラスに boolean 項目（既定は無効）を 1 つ宣言し、状態と戻り値の組み立てを使用箇所で `if` ゲートする**。評価専用のコード（判定ロジック・採点スキーマ・実行入口）は出荷パッケージに置かず、切り替え用の設定項目のみを出荷する（FR-037 / FR-065）
- 評価結果の保存は参照実装の `tests/extract_langsmith_data.py` に倣い、ローカルの 1 行 1 レコードの JSONL とする（FR-043）。参照実装が使う外部サービス（LangSmith）はアカウントを必須にするため採用せず、同じ情報をローカルに保存する（FR-045）
- 参照実装は評価専用の依存を `[project.optional-dependencies]` に隔離している（`pyproject.toml:17, 39`）。同じく、評価専用のライブラリが必要になった場合は開発用の追加依存に限定し、実行時依存は 0 件のまま維持する（FR-033 / FR-045 / SC-014 / SC-019）
- 評価結果の既定の保存先は `artifacts/eval/` とし、リポジトリの追跡対象に含めない（FR-043 / SC-027）。参照実装は結果を `tests/expt_results/` に置いてコミットする（実測: 3 件・1.3〜2.1 MB。README の結果表とコミット SHA に紐づく）が、対象は成果物をコミットしない既存の方針（`artifacts/` は `.gitignore` 済み、`script/analyze_structure.py` の出力先）に合わせる。この 1 点は参照実装と異なる。その結果、実行をまたいだ比較は同じ環境でファイルが残っている間に限られ、README への結果表の掲載は本仕様の範囲外とする
- 判定スコアの扱いは参照実装に合わせる（FR-039 / FR-067）。すなわち、型と必須項目は構造化出力に保証させ、点数の値域は判定モデルに委ね、**追加の範囲検査を設けない**。範囲外の値は記録に残るため集計時に検出できる。人の判断との一致（判定の妥当性そのもの）は範囲外である
- 判定の再試行の規則は全観点で同一とする（FR-068）。参照実装が 1 観点にのみ再試行を付けている非対称は、意図的な設計とは認められないため移植しない（FR-063 の「欠陥を移植しない」に該当する）
- 評価対象の指示セットは参照実装と同じく**名前付きデータセット**として扱う（FR-070）。ただし参照実装はデータセットの実体を外部サービス（LangSmith）に置いており、リポジトリに残るのは結果の JSONL のみである（実測: `tests/expt_results/` に 3 件、データセット定義はリポジトリに無い）。対象は外部サービスのアカウントを必須にできないため（FR-045）、**既定のデータセットをリポジトリ内の固定ファイルとし、外部データセットの参照は任意の経路とする**。この 1 点のみ参照実装と配置が異なるが、名前で指定する契約と結果の形（FR-071 / FR-072）は合わせる
- 評価結果の記録の形は参照実装に合わせ、識別子・指示文・成果物の 3 項目を 1 行 1 レコードで書き（`tests/extract_langsmith_data.py:40-45`）、ファイル名にデータセット名と対象の識別子を含める（`:50`）。採点結果は同じ識別子で結び付ける（FR-071 / FR-072）
- 参照実装の `examples/*.md`（obesity/arxiv・inference market × 2・pubmed）は README 用のサンプル成果物である。対象でも同等の位置づけのサンプルを置くかは本仕様の範囲外とし、強制しない
- 評価の観点は参照実装の 6 評価を基盤とする（FR-038）。ただし「正しさ」は参照出力（正解）を必要とし（`tests/evaluators.py:108-111`）、対象の指示（「〜のトレンドを 5 件」など）には一意の正解を用意できないため、**採点対象外として対応表に明示**し、残る 5 評価で観点数の要件を満たす（FR-074 / SC-033）。正解を人手で整備して「正しさ」も測る判断は本仕様の範囲外とする
- 評価の実走の入口に独立スクリプトを選んだ理由は、既存 CLI の互換性にある。対象の CLI は `instruction` が必須の位置引数のフラット構成で、オプションやサブコマンドの追加は利用者の呼び出し形式と既存テストの期待値に影響するため（FR-030 / FR-035）。評価は本リポジトリの日常の利用経路ではないため、出荷物に含めない位置に置く方が利点が大きい
- 設定項目の値域の宣言（FR-059 / FR-060）は、既存フィールドの削除・改名を伴わない。Studio の入力契約を強めるものであり、CLI の観測可能な契約（FR-030）は変えない
- 値域外の値と型違いは起動時に拒否する（FR-024 / FR-059）。参照実装は Studio の UI をスライダーにして範囲を UI 側で守らせ、環境変数の値域検査を持たない（`legacy/configuration.py` に `ge` / `le` は無い）が、対象は環境変数（`TR_*`）経由の誤設定で実行が停止しうるため（並列数 0 でセマフォが待ち続ける）、この 1 点は参照実装より厳しくする。丸め・既定値への置き換えは行わない（黙って別の値で実行される状態を作らない）。なお、既存フィールドに値域を追加した場合、従来受理していた値が新たに拒否されうる。これは終了コード 2（引数エラー）の範囲内の変更であり、既存テストの期待値を書き換えず、利用者向けの説明（README の終了コード表）に反映する（FR-035 / SC-012）
- 使用量の計測と評価基盤は、本仕様の他の要件（圧縮・再試行・縮退・自己点検）の効果を測る手段でもある。測れない変更を行わないことを本仕様の運用方針とする
- 判定（採点）に用いるモデルは `.env` / 環境変数（`TR_EVAL_MODEL`）で指定し、出荷する設定クラス（`Configuration`）には追加しない（FR-069）。参照実装は判定モデルを `tests/evaluators.py:8-10` のモジュール定数 `eval_model = ChatOpenAI(model="gpt-4.1")` に直書きし、かつ `ChatOpenAI` を直接構築して生成側の `init_chat_model` 経路と不揃いである。対象は OpenAI 互換プロキシ（`OPENAI_BASE_URL` と `x-opencode-session` ヘッダー）を通す必要があるため、判定モデルも `tools/llm.py` の経路で構築する（FR-045）。この 2 点（指定方法・構築経路）は参照実装と異なる
- 判定モデルはノード実行の設定ではないため、FR-024 / FR-025（実行時設定の唯一の型と単一解決経路）の対象外とする。`Configuration` に項目を足すと Studio の入力面と実行時設定の契約（FR-059 / FR-060）が「出荷物の実行」と「評価の実走」で混ざるため、環境変数のみで与える（FR-069）
- 実走の入口は、公開 API（`trend_researcher`（コンパイル済みグラフ）と `render_report`。`src/trend_researcher/__init__.py`）を in-process で呼び、`ainvoke` の戻り値（状態）からレポートと中間データを得る（FR-065）。参照実装は `client.aevaluate(graph, ...)`（`tests/run_evaluate.py:67`）でグラフを in-process 駆動しており、同じ形とする。CLI を subprocess として起動する方式は、stdout がレポートのみ（`FR-030`）で状態に到達できないため採用しない
- 実走の初期状態の組み立ては、CLI と同じ最小の 3 項目（`messages` = 指示文 1 件 / `platform` / 明示指定時のみ `max_results`。`__main__.py:87-93`）を実走スクリプト側で行う。CLI の引数解釈（`--since` の正規化など）は再利用せず、再実装もしない（評価の入力はデータセットの指示文であり、CLI の引数ではないため）。この重複は参照実装が批判された「設定の 3 重記述」のような過剰な複製ではなく、参照実装の `run_evaluate.py` が設定値を組み立てているのと同じ位置づけである
- 実走は CLI を通らないため、実行の待ち時間の上限（CLI の `EXECUTION_TIMEOUT`）やフィクスチャの場所・結果の保存先・判定モデルは、実走スクリプトの引数または環境変数で与える（FR-066）
- 2 構成の比較は、生成と判定を分離する（FR-041）。参照実装は構成ごとに別々に実験を走らせて保存し、あとから `evaluate_comparative((実験A, 実験B), ...)` に実験名のタプルを渡して比較する（`tests/pairwise_evaluation.py:124-128`）。対象もこれに合わせ、生成は構成ごとに 1 回・比較は保存済みの結果 2 件を名前で指定して行う。生成は 1 実行に数分かかるため、判定プロンプトの調整のたびに生成をやり直す手順は採らない。このため、比較対象の構成の違い（例: 自己点検あり / なし）は結果ファイルの名前に現れる識別子で区別できる必要がある（FR-072）
- 自己点検の切り替えは出荷される設定クラスの真偽値項目（既定は有効）とし、評価専用の構成切り替えを別に設けない（FR-054）。参照実装の `include_source_str` と同じ形（`legacy/configuration.py:42, 78`）をとる。「自己点検あり／なし」の比較（US6 / SC-024）はこの項目の値差だけで作れる。既定を有効とするのは、本仕様の目的が堅牢化であり、既定で点検が働くことを意図するため。既存の設定フィールドへの追加であり、削除・改名を伴わない
- 判定モデルの既定値（コードに持つ値）は、対象エンドポイント（OpenAI 互換プロキシ）で実際に利用できることを実測してから確定する。利用できないモデル名を既定にすると実走が開始直後に失敗するため、上限超過の検出（FR-064）と同じく実測を先行させる
